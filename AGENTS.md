# Wildcard — guide for agents

<!-- Follows the agent-instructions skill. Keep it under 200 lines. -->

Wildcard is an iOS app where friend squads check in every day (训练 / 健康餐 / 坦白放纵餐 / 今日请假条), see each other on a shared track, get a Sunday 战报 recap and share a weekly 3:4 schedule poster. Chinese-first UI. The MVP plan lives in the project's docs; this file holds how the code is built.

The shared rules and skills here come from `sponge-ai-lab/engineering-skills`. Change them there first, then copy the change in. The TypeScript skills (`verification`'s ESLint config, `module-structure`, `errors`, `zod`) apply to `web/`, `api/` and `supabase/` as written; the Swift equivalents are in **Language practices** below.

## Layout

- `ios/` — the app. `Wildcard.xcodeproj` is a thin app target; all logic lives in local Swift packages under `ios/Packages/`.
- `api/` — the HTTP API (TypeScript: Node, Hono, Zod, Kysely), the only way into the data. Supabase is its Postgres, Auth and Storage.
- `web/` — wildcardsquad.com, static files Vercel serves from `web/public` with no build step (root directory `web`). The site speaks Simplified Chinese unless the visitor picks another language (`web/public/language.js` remembers the pick on that browser). The home page (`/` in Simplified Chinese, `/zh-hant/`, `/en/`; `/zh/` redirects to `/`; brand surface, the squad's warm-up and the 冲线 headline) is written by `pnpm --dir web generate` from `web/pages/home.html`, with the squad drawn from the app's own art (`ios/Packages/Avatar/.../Placeholder`, looks in `web/character/cast.json`) and the wordmark font from `DesignSystemUI`; its scripts are in `web/public/home/` (`avatar.js` ports AvatarDomain). The invite page (`/join/<code>`, `web/public/join/`, by `web/vercel.json`'s rewrite) reads the public invite lookup from the browser (the API allows CORS from wildcardsquad.com on that route only) and shows the squad in the 排队入场 lineup (`web/public/character/`: `dress.js` dresses any look, `lineup.js` ports AvatarUI's `Lineup`); its button opens the App Store. `web/public/{,zh/,zh-hant/}{privacy,terms}` are the static privacy policy and terms in English, Simplified and Traditional Chinese (wildcardsquad.com/privacy, /zh/privacy, /zh-hant/privacy, and the same for /terms; the URLs App Store Connect and the app link to), with a French copy for Quebec under `fr/` and the consumer health data policy (Washington's My Health My Data Act) at `{,zh/,zh-hant/}consumer-health-data`, linked from every home page's footer; they never name the developer. `web/public/wildcard.css` holds the design system v4 tokens (including `--brand` and `--on-brand`, the app's brand colours), the wordmark font and the shared pieces for every public page (header, footer, gym floor, logo, the App Store button); change all three language versions together; when the policy changes in substance, bump the AI consent copy version too.
- `supabase/` — migrations, row-level security policies, edge functions (TypeScript).

## Commands

- All checks that run without a Mac (the cloud stop hook runs this): `scripts/verify.sh`. It runs `swift test` for every package in `ios/Packages/`, and the web, database and API checks once `web/`, `supabase/` and `api/` exist.
- Database: `scripts/verify.sh supabase` resets local Supabase from `supabase/migrations` and runs the pgTAP tests in `supabase/tests/database` (needs Docker and `supabase start`). CI runs it in a Linux job, since macOS runners have no Docker.
- API: `scripts/verify.sh api` installs `api/` with pnpm and runs ESLint, Prettier, `tsc`, dependency-cruiser (`pnpm --dir api boundaries`), `scripts/api-compat.sh` (the pinned oasdiff, `scripts/oasdiff-version`, comparing `openapi.json` with the base's and failing on a change installed builds can't read) and the Vitest tests, which use local Supabase's database and Auth (needs `supabase start`). After changing a route, `pnpm --dir api openapi` rewrites `api/apps/server/openapi.json`; a test fails while it is stale. Then `scripts/swift-openapi.sh` regenerates the app's Swift from it, the wire types (`ios/Packages/Contracts/Sources/APIContract/Generated`) and the client (`ios/Packages/Backend/Sources/Backend/Generated`), never edited by hand; `scripts/verify.sh` fails while they are stale. After changing a push, `pnpm --dir api push-samples` rewrites `ios/WildcardUITests/push-samples.json`; a test fails while it is stale. After a migration, `pnpm --dir api db-types` rewrites the Kysely table types (`src/adapters/tables.ts`) from local Supabase; `scripts/verify.sh` fails while they are stale.
- API journeys: `scripts/api-journeys.sh [check-in] [photo-upload] [squad] [disclaimer-drafts] [weekly-plan] [squad-today] [week-summary] [reactions] [comments] [devices] [daily-push] [weekly-awards] [coach] [account] [admin-mcp]` starts the built server against local Supabase and drives the `verify-wildcard` journeys over HTTP as the app would (needs `supabase start`); CI's `supabase` job runs it.
- App adapters, end to end: `scripts/verify.sh backend` starts the built API against local Supabase and runs `swift test` for `ios/Packages/Backend`, so the app's own sign-in and API client sign members in, save profiles, upload photos and post and read check-ins against the real API, database and Storage (needs `supabase start`); the `swift` part only builds it. CI runs it in the Linux job, whose image ships Swift.
- Website: `scripts/verify.sh web` installs `web/` with pnpm, checks the generated files are current, runs ESLint and Prettier, then the Playwright tests (layout at 320 to 1440px, taps, reduced motion, legal URLs). After changing `web/pages/home.html`, `web/character/` or the app's art, `pnpm --dir web generate` rewrites them; `pnpm --dir web serve` previews `web/public` at localhost:4321.
- iOS build, UI tests and screenshots (macOS with Xcode 26 or newer): `scripts/ios-test.sh`. It boots the simulator first, runs a failed UI test once more and lists any that passed only then at the end of the log, and writes the screenshots the UI tests keep to `build/ios/screenshots/`; `SHARD=k/n` runs the k-th of n parts of the test classes, balanced by `scripts/ios-test-weights`; CI's `ios` job runs it in three parts on three Macs at once and uploads the screenshots as one `ios-screenshots-<sha>` artifact.
- App compile only (macOS with Xcode 26 or newer): `scripts/ios-build.sh` builds the app, its extensions and UI tests for the simulator without running them.
- Avatar previews (macOS with Xcode 26 or newer): `scripts/avatar-preview.sh` renders the character through `AvatarUI` on an iOS simulator into `build/avatar/previews/` (outfit stills, cheer frames, GIFs, frame timings); CI's `avatar-preview` job (manual runs only) uploads them as `avatar-previews-<sha>`, and with `PRINT_PREVIEWS=1` prints them base64 in the log for agents that can't download artifacts.
- App on a local backend: `scripts/local-backend.sh` runs the API on 127.0.0.1:8080 against local Supabase and makes test members `member1@wildcard.test` to `member3@…` (password `wildcard-local`); a Debug build launched with `-local-backend -test-member member1@wildcard.test wildcard-local` signs in, signs up and checks in end to end in the simulator. Release builds use the hosted backend; Debug builds without the flag (and UI tests) run on the in-memory sample squad.
- Lint (part of `scripts/verify.sh`): `swift format lint --strict --recursive ios` (`.swift-format`) and `swiftlint lint --strict` (`.swiftlint.yml`). `swift format -i -r ios` fixes formatting. `scripts/install-swiftlint.sh` installs the pinned SwiftLint (`scripts/swiftlint-version`); with another version `scripts/verify.sh` ends inconclusive.
- Deploy (the beta): `.github/workflows/deploy.yml`, run by hand from `main` (Actions → deploy). It applies new migrations to the hosted Supabase project, builds `api/Dockerfile` and rolls it out on Cloud Run, served at `https://api.wildcardsquad.com` through Cloud Run's domain mapping, and refuses while a migration the hosted database already ran was edited. The server's secrets live only in Google Secret Manager (Cloud Run reads them; the deploy holds none and signs in through Workload Identity). `scripts/gcp-setup.sh` sets up the Google Cloud project in Cloud Shell, including the Cloud Scheduler jobs (rerun it when they change). The hosted project's Auth settings (site URL, OAuth server, Apple) are set by hand in its dashboard, as `supabase/config.toml`'s comments say. What to raise before a launch brings hundreds of members at once (Supabase plan and pooler, Cloud Run limits, the coach's caps, the jobs): `docs/scale-runbook.md`.
- TestFlight: `.github/workflows/testflight.yml`, runs every 3 hours on `main`, only when `ios/` changed since the last build that uploaded (best effort: GitHub may skip a scheduled run), and by hand from `main` (Actions → testflight), which always builds. It archives the Release app, signs it with automatic, Apple-managed (cloud) signing and uploads it to App Store Connect, numbering the build from the run. Cloud signing makes an Apple Development certificate on each fresh runner, so the last step (`scripts/asc-revoke-dev-certs.py`) revokes the new "Created via API" development certificate (never a Distribution one); without it the account's certificate limit fills and archiving fails. It signs in with an Admin-role App Store Connect API key, whose .p8 is the repository secret `ASC_PRIVATE_KEY`; the only other secret GitHub may hold is `SENTRY_AUTH_TOKEN`, an upload-only Sentry token the workflow uses, when it exists, to send the build's debug symbols to Sentry. `ios/Wildcard/PrivacyInfo.xcprivacy` must agree with the App Privacy answers in App Store Connect and with the privacy policy; change them together.
- TestFlight crash reports: `.github/workflows/testflight-feedback.yml` (Actions → testflight-feedback, by hand) runs `scripts/asc-feedback.py`, which prints the newest crash reports testers sent from TestFlight through the App Store Connect API: the device, OS, exception and crashed thread only, never the tester's name, email or comment, since the log is public.

## CI

The repo is public until launch, so GitHub-hosted runners are free, macOS included. `.github/workflows/verify.yml` runs `scripts/verify.sh` (job `verify`), `scripts/ios-test.sh` (job `ios`) and `scripts/avatar-preview.sh` (job `avatar-preview`) on `macos-26`, and the database and API checks (job `supabase`) and the website's checks (job `web`) on Linux. Ready PRs and pushes to `main` run the Linux checks (`verify` on Linux builds and tests the Swift packages), and every PR passes its checks before merge; nothing merges red. No PR uses a Mac (Tracy, 2026-11-08): a PR merges on the Linux checks, code review, verifier and Codex, and `ios` (the UI tests on three Macs for about 40 minutes) runs on `main` only, on a schedule every 3 hours for what `main` changed since the last scheduled run (nothing when it didn't change) and on manual runs (Actions → verify → Run workflow), which also run the macOS `verify`. The merge queue starts a manual run on `main` before each TestFlight and dispatches TestFlight only once it is green; a break it finds is fixed forward by the owner of the PR that caused it. `avatar-preview` runs on manual runs only. `verify` runs only when a PR changes the app's Swift or the OpenAPI file, and `supabase` only when it changes `supabase/`, `api/`, `ios/` or `scripts/`; a docs-only PR runs neither, and `web` runs for any PR that changes the site or what it is generated from. Pushes to main use the same rule against the commit before, so a merge uses no Mac. CI cancels a PR's run when a newer push to it replaces it; "green" means that check passed on the PR's head. Run `scripts/verify.sh` in your session before every push too; where a toolchain is missing there, CI's result is the evidence. Keep CI fast: a job should run only for the paths it checks, a new check that can run on Linux goes in a Linux job, and fixes are checked locally and batched into one push, since every push queues for the few macOS runners. Never add a self-hosted runner while the repo is public: a fork's PR could run code on that machine. Never commit secrets, keys or private data; anything pushed while public stays public. Before launch the repo goes private, and the macOS builds move to Xcode Cloud.

How it is tiered, what each component is for and when a piece belongs in it: `ios/Packages/DesignSystem/README.md`. ## Language practices

SwiftLint and swift-format enforce style; they are not repeated here.

- Swift 6 language mode with strict concurrency (needs Xcode 26 or newer; the app targets iOS 26). No `@unchecked Sendable` without a comment saying why it is safe.
- **Module boundaries are packages.** A package imports another only through its public API; `Domain` targets never import SwiftUI, UIKit, `Backend` or `APIContract`. Cross-capability types live in a small `Contracts` package.
- **Reuse before you add.** Search first. Shared code goes in a package named after its topic, never `Utils`, `Shared`, `Common` or `Helpers`.
- Parse at boundaries with `Codable` into strict types; stored and wire JSON carries a top-level `version`.
- Errors: one `enum` per package conforming to `Error` with a specific case per failure the caller can act on; use typed `throws(PackageError)`. `fatalError` only for broken invariants.
- Domain code never reads the clock, generates ids or does I/O directly: inject `Clock`, id generators and ports.
- No force unwraps (`!`) or `try!` outside tests.
- **Native first** (Tracy, 2026-11-05). Where iOS has the component or behaviour (navigation and its back swipe, sheets, pickers, scrolling), use the system's, never a hand-made look-alike; build our own only where an approved design asks for something the system can't do. Pages that open over another are pushed on the tab's NavigationStack (`DesignSystemUI`'s `pushedPage`).
- **Motion and feel are features.** Animations run at 60fps or better on device; no work on the main actor that can drop a frame. Haptics come from `Haptic`: one per meaningful moment, never on every tap.
- **Encode lessons in structure.** Prefer a type that makes a bad state unrepresentable, then a lint rule, then a runtime check.
- Public-facing copy never mentions internals.

## Testing and verification

- **Prove it works.** Run the feature the way users do before calling it done. UI changes attach simulator screenshots or a recording to the PR.
- **Look at every screenshot before it leaves your hands.** The author, and again the verifier, checks each one (smallest supported phone, long text where the screen has any) for content that is clipped, cut off, covered by buttons, keyboard or tab bar, or overlapping. Any such flaw is a FAIL, not a note. Where layout is at risk, add a UI test asserting the content's frames stay inside the visible area and clear of the controls over it.
- Domain tests use Swift Testing (`@Test`, `#expect`) with literal expected values. Backend tests run against local Supabase in Docker, never a mocked database.
- **Build what was approved.** The Approved designs collection (linked from the project instructions) holds the latest design the owner approved for every screen and flow, and is the source of truth for UI; it is updated the day a new design is approved. A new screen or a big redesign shows the approved design and the actual screen side by side before merge; a small UI change is compared on the next scheduled `ios` run on `main` (CI). Any difference the owner didn't agree to fails verification; what can't match is told to the owner before merge, never shipped as a silent placeholder. Scene colours are not differences: they come from the squad's theme. The gym theme is the default everywhere a squad hasn't picked one (sign-up, the sample squad, UI tests), so screenshots compare with the designs.
- **Someone else passes it, as deep as the change is risky.** The owner picks a tier from the diff and names it in the PR: CI only (docs, tests, a small fix with its test), light (a small UI change or one module's logic; the verifier reads the diff, CI and screenshots and tries an edge case) or full (contract, schema, auth, privacy, user data, AI, a new flow, across modules). A verifier is a fresh agent that did not write the change; it gets only the task and the diff, works from a clean checkout of the pushed commit, and returns PASS, PASS+NOTES or FAIL with evidence, naming the head commit and the diff hash from `scripts/verify-diff-hash.sh`. It starts when the PR is marked ready, alongside CI, quotes CI's result for the head instead of rerunning it, and spends its time on what CI can't show. One run per diff, on the PR's head only, never again on `main` after the merge; after a fix it checks only the delta, unless the fix reaches past the findings or touches the contract or schema. CI, a code review and the author's own review are not a verdict. How, in `raise-pr` (Independent verification).
- Every thread runs `scripts/verify.sh` (or the relevant local checks) before every push; where a check can't run in your session, say it is inconclusive and let CI be the evidence.

## Pull requests

- Branch from `main`. One small change per PR. **Never stack** a PR on another open PR.
- Run `scripts/verify.sh` first. Open the PR as a draft and mark it ready once it passes: CI runs only on ready PRs.
- **No light- or full-tier PR merges without a verifier's PASS or PASS+NOTES for its current diff.** A FAIL goes back to the author, or to a human if the author disputes it; a change to the diff after the verdict needs a new verdict from a new verifier.
- Write it with the `raise-pr` skill. The **Verification** section lists each command you ran and what it printed, or "inconclusive" and why. Anything users see carries screenshots or a recording.
- **Get a code review once the PR is ready, and again only when a new head needs one.** A fresh Claude agent that did not write the PR reviews the green head under the Code Review Rules below; tier 1 PRs (docs only, tests only, a typo, or a small fix with its test) skip it and rely on CI. Bigger PRs (features, API, contract or schema, architecture, new dependencies, large refactors) also get one `@codex review` comment after CI and the verifier both pass, which never holds a merge more than 30 minutes; at most two per PR, since Codex usage is limited. How, in `raise-pr`.
- **Match the model to the work, since tokens are limited.** Simple, mechanical work runs on Sonnet: code reviews, light verification, docs, lists, status and diagram updates. Writing real code and design work stay on Opus. When you start a subagent for simple work, pass `model: "sonnet"`.
- **Review feedback is a symptom, not a to-do list.** Every finding (a person's, a bot's, a verifier's note) is a claim to check before acting; answer each on the PR, fixed (with the commit) or not and why. Read the whole review first and group findings by cause. When a PR gets findings a second time, post one short root-cause note before pushing a fix, then rework it into the simplest design. When in doubt, ask a human.
- **Who merges:** the owner thread merges every PR itself, AGENTS.md, contract and schema PRs included, once CI is green and the review and verifier its tier needs have passed; it never waits for Tracy to merge (Tracy, 2026-10-23). The exact rule is in `raise-pr` (Merging).
- Only change what the PR is about. Never force-push `main`; never edit or delete other people's comments.
- **Keep parallel PRs from lagging.** Land small shared PRs first so others build on them; before removing public code, check the other open branches for users of it; merge `main` into a PR once, right before its merge, not after every merge on `main` (that restarts its checks for nothing); a clean merge of `main` doesn't need a new verdict (`raise-pr`).
- **A change removes what it replaces.** When a decision changes, the PR that builds the new way deletes the old one everywhere (app, API, database, docs, AGENTS.md), even in other packages. Removing it is in scope; a PR isn't done while the old path still exists.
- **The API stays readable by every installed build** (TestFlight testers are real users). Only add to `openapi.json`: never remove or rename a reply's field, make one optional, add an enum value to a reply, or remove a route while a build that uses it may be installed; `scripts/api-compat.sh` (part of `scripts/verify.sh api`) fails on any of these. To retire something, stop the app using it, keep serving it, and remove it only once no installed build needs it, listing the change in `api/apps/server/openapi-breaking-allowed.txt` in that PR. Database migrations and the app's stored shapes may still be edited in place until launch.
- **When a parallel PR lands, the later one wires them together** (or opens an issue saying what is left unwired).
- **If agents can't agree** after one round of replies, post a **Decision needed:** where the discussion is (`wildcard-docs`) and stop work on that point until a human answers.
- **Ground decisions in evidence:** link one to three credible sources (Apple, Supabase, standards, well-known engineering blogs), or say there are none.
- **When a decision or review comment would hold in any project,** also open a PR adding it to `sponge-ai-lab/engineering-skills`.

## Friction

- **Report friction the moment you hit it.** When the architecture, a boundary or an abstraction makes the work harder (a workaround, a rule written twice, a port that can't say what you need, a change that ripples through many packages), open a GitHub issue labelled `friction`: what you were doing, what got in the way, the workaround, and the fix you'd suggest. Keep going with the smallest clean workaround; don't start the refactor yourself. Then tell the friction owner the project instructions name.
- **The friction owner reviews each report against the whole list.** On a recurring theme or a severe report with a clear fix, it acts at once; otherwise it asks a human to decide.

## Code Review Rules

Flag only real problems: bugs, broken rules, missing evidence. Formatting and anything SwiftLint, swift-format, ESLint or the compiler already catches are not findings.

- A `Domain` target importing SwiftUI, UIKit, `Backend` or `APIContract`, or a package reaching into another's internals.
- A hand edit to generated code (`APIContract/Generated`), or a wire type written by hand instead of generated.
- A new helper that duplicates existing code, or lands in a `Utils`/`Shared`/`Common` package.
- Domain code that does I/O, reads the clock, or generates ids itself.
- Stored or wire JSON without a top-level `version`.
- A force unwrap or `try!` in shipped code, or `@unchecked Sendable` without a reason.
- A hard-coded user-facing string outside the String Catalog (other than the 战报 words the API sends).
- A new screen or big redesign without screenshots or without the approved design beside them, a test that can't fail, or a mocked database.
- A PR based on another open PR, or one that mixes unrelated changes.
- A verification tier lower than the diff warrants (`raise-pr`, Independent verification).
- Code the change leaves dead or duplicated (an old rule kept after it moved, a second type for the same thing), or an old name after a rename.
